# 可适配替换清单 · dsh · 2026-11-18

> 依据需求规格 §6.0 产出。用途：一是对 dsh 落位路径做现场勘察，关闭 §9-1 技术阻塞；二是作为首份真实清单验证勘察流程可实施。**本清单是勘察产物，不是落位操作**——未写任何 dsh 配置。

## 勘察结论速览

**推翻需求文档原判断**：文档 §5/§9-1 写"dsh 不读 persona 文件、系统提示由 cordis.patch.yml 组装、必须走编译注入"，实读证实**错误**。dsh 原生自带完整 persona 注入体系，**三条落位路径可用**，无需自建注入引擎。

## 🚧 待确认项（人裁定后才能落位）

1. **P1 的 patch 写法**：改 preset 内 persona 行需在 `cordis.patch.yml` 里按 `id` 精确 patch（已知 patch 按 id 定位，见 MAGPIE 接入教训）。是改四个 preset 全覆盖，还是只改当前默认 `standard`？改全部会连带影响 minimal 的 `complete:true` 语义。
2. **soul.md → prefix 的编译边界**：persona prefix 是模板，完整 `{{…}}` 组在渲染时解析为提示词变量。soul.md 里的 `{{` 字面量要转义吗？换行与多段如何排版？
3. **契约类的最优落点**：contract/* 是合并进 P1 的 prefix（成为人格的一部分，token 恒定），还是走 P3 追加到 `AGENTS.md`（工作区指令，可被预算裁剪）？前者更稳，后者更贴合"契约是规则不是人格"的语义——🚧 需拍板。
4. **P3 全局 vs 项目级**：若选 AGENTS.md 追加，`~/.dsh/AGENTS.md`（所有会话生效）还是项目工作目录（仅该项目）？注意工作目录若是收口目录，其 AGENTS.md 是外层根规则，不可混写。
5. **`dsh-persona` 仅限 scope 内**：全局挂载会与提示词注册表相撞并明确报错——所以 patch 必须落在 preset 的 plugins 内，不能顶层挂载。这是硬约束，已确认，无需裁定，记录在此防止误操作。
